**Outcome.** `@vigla/kit` and the adapters `@vigla/adapter-node`, `@vigla/adapter-bun` and `@vigla/adapter-static`, written anew in TypeScript, do what SvelteKit 3.1.0 and its node, bun and static adapters do for runes code ([[e34c15e3]]), installed under the aliases `@sveltejs/kit`, `@sveltejs/adapter-node`, `@sveltejs/adapter-bun` and `@sveltejs/adapter-static`. Kit imports the core `vigla` and `@vigla/vite-plugin`, never a front end: route components arrive compiled by whatever front end the Vite plugin found, and Kit's own components are template IR compiled by `vigla/compiler`.

**Packages.** `packages/kit` (`@vigla/kit`, version line 3.1.x so that libraries' `@sveltejs/kit` peer ranges hold and `VERSION` equals the manifest's `version`), `packages/adapter-node` (6.0.x), `packages/adapter-bun` (1.0.x), `packages/adapter-static` (4.0.x). Like the core, the workspace packages export their `.ts` sources; Node strips types because a workspace link's real path lies outside `node_modules`.

**Kit keeps Kit's public names.** What an app writes or a tool reads is Kit 3.1's contract and keeps its spelling: `$app/*`, `$env/*`, `#lib`, `data-sveltekit-*` attributes, `x-sveltekit-*` headers, `__data.json`, `_app/immutable`, `.svelte-kit` and its `output` layout, `sveltekit()` from `@sveltejs/kit/vite`, `#svelte-announcer`. Code Kit generates names Kit by the name the app installed it under (`@sveltejs/kit` or `@vigla/kit`), found by resolving the package from the Vite root. Format names the core writes into pages — the hydration-data global, element metadata — are the app's front end's ([[ec26636a]]): Kit passes that front end's `Format` to `render()`, `hydrate()` and the compile of its own components, the core's own names when the app has no front end. That `Format` comes from the front end's `vigla.frontEnd` declaration through `@vigla/vite-plugin`'s plugin API, a contract to add with the plugin's and the adapter's owners.

A module of Kit imports another only through its entries; the core is reached only through `vigla`'s published entries (module `entries`); nothing in Kit imports `@vigla/svelte` or a `svelte` specifier, enforced by the import rule as for the core. Unit tests live beside the code they test and are the `covered` targets the manifest names.

**The server runtime is Web-only** ([[e34c15e3]]). `kit-server`, `kit-shared`, `kit-types` and the server files of `kit-entries` load no Node built-in — no `node:*` or bare built-in specifier, no `process.getBuiltinModule`, no `process`, `Buffer` or `require` — enforced at gate by an inspection in `tagma.config.ts` and a `#rule` sourced to those directories. What upstream reaches through Node there comes from the platform instead:
- the request store `getRequestEvent()` reads after an `await` comes from an async-context port `Server.init({ scope })` takes — `{ run(store, fn), getStore() }`, the subset of `AsyncLocalStorage` Node and Bun pass unwrapped and which the dev server, the prerenderer and adapter-node and adapter-bun pass. Without one, the store is read synchronously only: inside the synchronous part of a hook, `load`, action or endpoint, and inside components through the request owner;
- source-mapped stack traces in dev are the dev middleware's (Vite's module runner), handed to the server as a `fixStack` option;
- environment variables arrive in `init({ env })`; `read` for `$app/server`'s `read()` is passed by the adapter.

**Request pipeline.** `new Server(manifest)`, `server.init({ env, read, scope })` once, then `server.respond(request, { getClientAddress, platform, read })` → `Response`. One request runs these steps, each a function of `kit-server` with its own owner:
1. *Classify* the URL: strip `paths.base`; recognize a data request (`/__data.json` with `x-sveltekit-invalidated`), a route-resolution request (server-side route resolution), a remote call (`/_app/remote/<id>/<name>`), an immutable asset path, `.html` and the trailing-slash rule; decode once.
2. *Route*: `reroute` (sync or async), then match the route table in its sorted order, params checked by the app's matchers.
3. *Scope*: create the request owner (core `root()`), the `RequestEvent` (cookies jar, `setHeaders`, `locals`, event `fetch`, `platform`, `tracing`), and the request store; set the store on the request owner's context and in the async-context port.
4. *Handle*: `handle` with `resolve(event, { transformPageChunk, filterSerializedResponseHeaders, preload })`, CSRF checked before it.
5. *Resolve* by kind: endpoint (method dispatch, `HEAD`/`OPTIONS`, content negotiation with a page on the same route), page (actions on `POST`, server then universal `load` per node in parallel with `parent()` ordering, SSR, the page payload), data (server `load` results with invalidation and streamed promises as NDJSON), remote (query, batch, live query, command, form, prerender, each validated by its schema), errors (`handleError`, nearest `+error` with the root's fallback to the `error.html` template), `handleFetch` for event `fetch`, server-side `fetch` replay data for the client.
6. *Finish*: cookies and headers applied, `vary`, CSP headers, ETag for prerendering, `HEAD` stripping; the request owner is disposed when the response body ends or the request aborts, running every teardown created under it.

**Pages.** The root component receives `{ page, tree, form, error, onerror }` — `tree` the nested layout/page nodes with their error components and data, as cells — and `kit-server` calls `render(root, { props, context, csp, transformError, format })` under the request owner, awaiting it with async always on. The document is the app's `app.html` compiled into a template function; head holds the stylesheet and `modulepreload` links, the head the render returned (the core's hydration-data script first), and Kit's payload script: the serialized server data, form, error, and `start(...)` of the client entry; deferred server-load promises stream as later `<script>` chunks into an open body. CSP nonces and hashes cover Kit's scripts and the core's (`hashes.script`). `ssr = false` renders the shell only; `csr = false` sends no client script.

**Kit's components.** The root nests node components through a recursive snippet, each node under a boundary whose failure renders the node's `+error` with `onerror` reporting it, binds each instance for `snapshot`, and shows the `#svelte-announcer` region after the first navigation; the default layout renders its children; the default error page prints `page.status` and `page.error?.message`. `kit-components` builds each as a `ComponentUnit` — expressions parsed with `vigla/compiler`'s `parseExpression` and `parseProgram` at offsets of a source text it assembles, runes marked in the unit's map — and `kit-vite` compiles each for the environment importing it, with the app's `Format`, serving the output as a virtual module. One compiler produces both sides, so the hydration markers agree by construction.

**Client.** The page payload calls `start(app, target, hydrate)` of the generated client entry. `start` creates the tab owner (core `root()`), runs `hooks.client`'s `init` under it, decodes the payload with the app's `transport` decoders, runs universal `load` for the initial nodes and hydrates the root under the tab owner with the app's `Format` — or mounts it when the server sent no SSR. The router owns history and link interception (`data-sveltekit-*`), the navigation lifecycle (`beforeNavigate`, `onNavigate`, `afterNavigate`), `goto`, `invalidate`/`invalidateAll` with dependency tracking (`depends`, url, params, route and `parent` reads), `preloadCode`/`preloadData` by hover, tap, viewport and eager options, scroll and focus restoration, `snapshot` capture and restore per history entry, hash routing, and server-side route resolution. `$app/state`'s `page`, `navigating` and `updated` are objects over core `cell`s. Remote-function clients keep one cache per tab: `query` with refresh, set and optimistic overrides, `query.batch`, `query.live` over SSE, `command`, `form` with fields and issues, `prerender`; values the server rendered reach them through the core's `hydratable` under the tab owner.

**`load`, actions, hooks and remote functions** keep Kit 3.1's semantics; what Vigla adds is where they run: each runs under the request owner on the server and the tab owner on the client, so `getOwner()` answers that owner in their synchronous code and context set on it reaches every component of the request or tab. Remote modules (`*.remote.ts`) are transformed by `kit-vite`: on the server each export is registered under a stable id derived from file and name; on the client it becomes a client of that id; with no flag, as [[658ccea4]] settles.

**Prerendering.** After the server build, `kit-build` loads the built server, analyses every server node, crawls from `prerender.entries` and each route's `entries()` through `Server.respond` with prerendering state (`building`, `prerendering`), follows links and `srcset`s, writes pages, data and endpoints into `.svelte-kit/output/prerendered`, and calls `handleHttpError`, `handleMissingId`, `handleEntryGeneratorMismatch` and `handleUnseenRoutes`. A prerendered request's `url` refuses `search` as upstream's does.

**Adapters.** `kit-build` hands an adapter the `Builder` Kit 3.1 defines — routes, prerendered pages, output directories, `writeClient`, `writeServer`, `writePrerendered`, `generateFallback`, `generateEnvModule`, `createEntries`, `compress`, `instrument` and the rest — over the output layout `.svelte-kit/output/{client,server}` upstream adapters read. adapter-node ships a Node server: `@sveltejs/kit/node` glue, static files with immutable caching and precompressed variants, its env options (`ORIGIN`, `PORT`, `HOST`, `PROTOCOL_HEADER`, `HOST_HEADER`, `PORT_HEADER`, `ADDRESS_HEADER`, `XFF_DEPTH`, `BODY_SIZE_LIMIT`, `SHUTDOWN_TIMEOUT`, `IDLE_TIMEOUT`, socket activation), `AsyncLocalStorage` as the scope, and its `handler` export. adapter-bun serves through `Bun.serve` and `Bun.file`, with `COMPILE` building a single executable. adapter-static writes the prerendered output and the fallback page and refuses unprerenderable routes under `strict`.

**The per-request owner and the app seams** ([[8191e72f]]). An app graph such as `@runlith/layer` needs no workaround:
- *per request*: the request owner is created in step 3 and disposed in step 6; `render()` runs under it through the core's owner per `render()` call ([[914a1860]]), so a graph set on it in `handle` is read by every component of that request with `getContext`, and `$app/server`'s `getRequestOwner()` answers it wherever `getRequestEvent()` does;
- *per tab*: the tab owner holds the client app for the tab's life; `init` runs under it and every navigation's components live under it;
- *snapshot from `load` to the browser*: the core's `hydratable(key, fn)` keeps its data on owners; Kit opens the store on the request owner, so a value registered in a hook, a server or universal `load` or the render is written into the document with the render's hydration-data script, and the tab owner reads it while the first document hydrates — `init` and the initial universal `load`s included. This needs the core to open a hydratable store on an owner on both sides, which [[914a1860]] delivers with the server side;
- *a place's chunks before navigation*: the route table is loaded with the client entry, so `preloadCode` and `goto` work from `init` on, queueing until the first navigation lands, and `preloadCode` resolves a route's layout, page and stylesheet modules without data.

**The harness's Kit part moves to `@vigla/kit`** ([[49056597]]). `targets/vigla/kit` installs `@sveltejs/kit` as `workspace:@vigla/kit@*` in the first change in which the recorded Kit set — today 47 unit and 7 type entries on upstream Kit 3.1.0 — passes on Vigla's package; until then it keeps upstream Kit. Each adapter switches to `workspace:@vigla/adapter-*@*` in the change that records its first entry. The `covered` reasons of Kit's unit specs name Vigla's Kit module ids. App, build-errors, prerendering and adapter entries are recorded app by app, in dev and build, in the change that first makes them pass. The remaining Svelte 4 construct in the apps — `<svelte:window on:popstate>` in basics' `routing/preloading/hash-route` — is converted with its reason recorded. The build-errors entry asserting that `*.remote.js` needs `experimental.remoteFunctions` becomes a difference: Vigla has no flag. Runs of whole apps with browsers and dev servers follow [[7fda0315]] and are announced to the lead before they start.

**Stages**, each landed when its entries pass:
1. This spec, the area note and module cards, the packages' skeletons, the Web-only rule enforced at gate.
2. `kit-shared`, `kit-types`, the public `@sveltejs/kit` entries, `kit-node`: the 47 unit and 7 type entries pass on `@vigla/kit`, and the target switches.
3. [[914a1860]]: an owner per server `render()`, context and the hydratable store on owners, mounts linked under the current owner.
4. `kit-config`, `kit-sync`, `kit-components`, `kit-vite` dev, `kit-server` pages, endpoints and data, `kit-client` start, hydration and router: basics passes in dev.
5. Builds, `kit-build`, prerendering and the three adapters: basics in build, prerendering, build-errors, the adapter apps.
6. Remote functions, forms, service workers, tracing and the remaining options: the async, options, options-2, options-3, no-ssr, no-csr, embed, hash-based-routing, dev-only, writes and prerendered-app-error-pages apps.

- Kit's unit, type, app (dev and build, each Playwright project and variant script), build-errors, prerendering and adapter entries in scope pass on `targets/vigla/kit` with `@vigla/kit` and the three Vigla adapters installed.
- The Web-only rule is enforced at gate with no debt, and no Kit module imports a front end.
- `basics`, converted to runes with its conversions in the manifest, builds and passes on the aliased install.
- A test of Vigla's own runs a request whose `handle` sets a context value on the request owner, reads it in a component and after an `await` in a server `load` through `getRequestOwner()`, and sees the owner's teardowns run when the response ends; another hydrates a `hydratable` value registered in a server `load`.
