The DOM and compiled code hold a batch through one primitive, `work()`: a unit of pending work in the current batch — the one an async continuation restored, the one in its structure or commit phase, else the open one, as for writes — returning the function that settles it once, in whichever batch the first has since merged into. The unit also settles when the owner that started it is destroyed: work whose tree is gone holds nothing, or a promise that never resolves would keep its batch uncommitted forever and every later batch in multi-batch mode. A unit holds its batch unless its owner lies under a branch the batch skips or an off-screen branch the batch did not select, or the owner's boundary chain has a boundary showing its pending content: content not yet on screen cannot be torn by a commit, so the batch commits and the boundary swaps the content in when its own count returns to zero. Once content is on screen, work under it holds the batch, so the old content stays until the new values arrive. Every unit is counted on the owner's nearest boundary, which `$effect.pending()` reads a microtask later.

`asyncDerived(fn)` holds nothing on its first run: the caller that awaits its first value holds the work until what depends on it exists, because a unit settled at resolution would let the batch commit before the template reading the value was created. Each later run is a unit of the batch that ran it, and its value belongs to that batch, so two batches awaiting the same expression each commit their own result. Runs retain the input values they actually read, including resumed segments, so a batch can validate its existing request without repeating it merely because another run of the expression executed. A late older result may update only its own uncommitted view while a newer resolved value stays current; it cannot publish after that newer result commits. Superseding a run within its batch settles its unit without waiting for the obsolete promise; its result is dropped. A merge adopts the incoming run, pending or completed, and supersedes the earlier run for that expression instead of requesting it again. Its aliases are one continuing batch: a later run started through the older identity may replace the adopted publication and its dependencies. A discarded fork's result is dropped. A normal rejection before the first value rejects the returned promise, and one after it settles its unit and then reaches the boundary. The runtime's stale-reaction cancellation leaves that run pending instead: a subsequent successful run or a merge supersedes it, so cancellation neither publishes an error nor commits a partial value.

A `Boundary` is the DOM's, seen here only as its parent, whether it is showing pending content, the count it is told of and the errors routed to it: an effect created under it inherits it, an error thrown by such an effect's run reaches `failed`, and a user effect created while it shows pending content waits until `reveal` runs it in the batch revealing the content. `suspend()` before an `await` and the function it returns after it restore the owner, the batch and that batch's view for the synchronous segment; `resumed()` ends that segment.

Inside an `asyncDerived` run the restored segment also reads for the run: what it reads becomes a dependency of the run's reaction, since a value read after an `await` decides the result as much as one read before it, and it is read in the batch that started the run (`async-context-batch`). That reading ends with the segment itself — at the next suspension, or where the compiled expression calls `unsave` at its end — never at a later microtask: a foreign microtask queued in between would subscribe the run to what it reads and, writing, be refused as a write from inside a derived (`async-save-foreign-microtask-mutation`). A rerun keeps the previous run's dependencies past its synchronous part, because the reads after its awaits are not made yet; dropping them there would let a write in another batch miss the expression. Once the newest published result has committed and no pending run remains, dependencies neither that run's synchronous part nor its resumed segments read are dropped; an ignored older completion cannot reinstate them.

A unit started outside a fork also counts toward `settled()`, holding or not: work under a boundary showing its pending content commits nothing yet, but the content it brings in is part of what `settled()` waits for (`pending-snippet-switch`).
