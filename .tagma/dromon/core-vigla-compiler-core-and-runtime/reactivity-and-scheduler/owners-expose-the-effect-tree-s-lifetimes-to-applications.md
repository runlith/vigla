`root(fn, parent)` and `owner.root(fn)` create an application lifetime in the scheduler's effect tree, linked only to its explicit parent; a calling reaction never adopts it. An owner releases its children from the newest back: each application root alone, each stretch of other children between them in creation order. The walk resumes from the newest live child after every release, so a teardown that disposes or adds a sibling cannot cut it short. A service therefore outlives everything created after it under the same owner — later services, components, mounts and teardowns, whose cleanup may still call into it — while component instance roots and ordinary effect siblings keep upstream's creation-order teardown among themselves. `owner.onDispose(fn)` registers such a teardown, reading current values like `onDestroy`; withdrawing it removes it, and registering on a disposed owner runs it at once, reading current values too. `onDestroy` with no owner is refused with `teardown_without_owner` on client and server: a registration nothing would ever release is a lost cleanup. `getOwner()` also exposes an existing current effect's lifetime, so a handle obtained lazily cannot change what it owns.

A local context layer is materialized only for a handle or a context write, keeping ordinary effect creation and context lookup on their inherited layer pointers. Materializing it retargets existing descendants still sharing the old inherited layer; a child's own layer keeps its values and receives only the new parent link. Traversal stops at local or separately captured layers, and isolated server renders retain their context boundary. Late handles and late ancestor writes therefore reach existing children without allocating a context layer for each branch or row. A server render materializes its handle before pushing component layers; child owners capture the active render stack rather than whatever component layer happens to be current later.

`owner.run` suspends the caller's dependency-reading and state-creation scopes. `owner.start` additionally counts work toward settlement until completion or disposal, while returning the callback's result or rejection; it holds no batch, so writes made while service work is pending reach the screen at once. Holding a batch is the separate act `hold(fn)`, the unit compiled `await` takes ([[1a1dd2a2]]); on the server, where no batch exists, it only counts. `owner.settled()` waits for the counted work under that owner and its descendants, on client and server alike, and for nothing another owner started; the free `settled()` waits for the whole application of the owner it is called under, and for all of it when called under none ([[4ece65b4]]). An idle subtree is confirmed once more a microtask later, after a flush already requested by a write has started the reruns that write queued, so `cell.current = next; await owner.settled()` waits for a resource that write restarts. Without a platform async store, ordinary JavaScript continuations carry no owner and re-enter explicitly through `owner.run` after an await. With one installed, `owner.run` also carries its owner across `await` ([[fc8a77b5]]). On the server every owner read takes one answer: the synchronous owner, else the carried one. That covers `getOwner`, context, `onDestroy`, `getAbortSignal`, the hydration store, and what `render()`, `derived`, `resource`, `hold` and external subscriptions attach to. `getOwner()` therefore never names an owner that creation then ignores. `root(fn, parent)` reads none: its parent is explicit. The owner's lifetime signal aborts on disposal; cancellation of the underlying operation is cooperative through that signal. Handles and failure registrations are weakly keyed by their effects, without a runtime registry retaining finished application scopes. Server effects do not run, but owners, context and lifetime disposal remain available around rendering.
