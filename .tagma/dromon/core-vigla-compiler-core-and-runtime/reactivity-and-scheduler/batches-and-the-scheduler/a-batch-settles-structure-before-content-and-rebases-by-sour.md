A batch is the unit of commit: the writes made since the last flush (each source's value `before` the batch's first write, and once the batch is held or a fork its own latest value `after`), the effects they dirtied, the structure changes its blocks register for commit, and the blocking work still pending in it. Writes made outside a flush go to the one open batch, created by the first write that changes a value and flushed at the next microtask or by `flushSync`. A batch whose blocking work is pending after its structure phase is *held*: it keeps its registered structure changes and the effects it collected, stays among the uncommitted batches, and is processed again once its work settles or something queues into it. A *fork* is a batch that holds until `commit()`, its writes kept in `after` alone and never applied to the sources' values. Committing it applies them and dirties what lies downstream, except an effect whose last run was under the fork's view and that nothing has dirtied since: that run already saw the committed values, so a block does not run twice and an async expression the fork started is not requested again; a derived the fork only computed through its view keeps its real cache and is invalidated by the committed writes, while an explicit derived assignment that no later fork dependency write invalidated commits as its current value. A fork whose traversed roots are all destroyed, or that touched none, leaves the uncommitted set until `commit()` takes it back, so an abandoned fork never puts later trees in multi-batch mode. What a fork's runs create stays apart from what the committed runs own until the fork commits or is discarded ([[389a8e9e]]).

**What a flush sees.** A source's own value is always its newest write outside forks, which is what code outside a flush reads. A batch reads those values directly until it retains its own values or another uncommitted batch exists. A retained view stays necessary even if a merge leaves the batch alone: unrelated and later uncommitted writes hidden behind their `before` values, an earlier intersecting real batch's writes inherited as the continuing cohort's base, and its own `after` values over any later write, a fork's writes visible only in the fork's own view and hidden from every other view at their real value, so that a run reading one is recorded against the fork like any hidden read. Before queued descendants use an inherited cohort view, structural ancestors depending on that cohort must establish the receiving batch's selection; an earlier batch's clean status cannot stand in for it. Existing per-batch reads still validate an owned selection under equality, and admission alone does not restart async requests. A write made into another batch while a view is in use — a content-phase write going to the next batch — stays hidden from that view. A derived whose run reads a hidden value, through an old dependency or a new one, is computed afresh in the view and cached there, never in the derived, which stays dirty for the committed world. A derived whose run in a view ends with no dependencies at all is cached in the derived itself, as upstream writes a dependencyless derived even in a fork: no batch's writes can change it, and leaving it dirty would let the committed world build a second object after a fork built the first (`fork-derived-class-instance`). A run for a fork, or one that read a hidden value, adds what it reads to its dependencies without dropping any, so a discarded fork or a later commit cannot leave a reaction blind to a source the committed world reads; any other run under a view computed what the committed world would and reconciles its dependencies as usual, so a leaked fork changes nothing for unrelated code. A batch that commits leaves the uncommitted set, so no later view hides what the DOM already shows (invariant 1); one held only by work under a boundary showing its pending content is not held at all and commits at once.

**Merging.** A batch first runs its structure under its own view, with its writes taking precedence over earlier held writes. Only when it has no blocking work after structure may it merge into the newest earlier held batch that wrote the same source, before committing any structure of its own. Choosing the nearest writer preserves chronology when several independently awaiting batches wrote that source. A batch with work of its own stays separate, so independently awaited writes can commit as their own work settles. The merged batch hands over queued and forced effects, deferred content and effects, registered changes, pending work units, waiters and recorded runs, and stays reachable as an alias so continuations and work settlement reach the batch it joined. Its async runs replace the earlier runs for the same expressions without making new requests; other structural reactions reached by the merged writes rerun under the combined view. Writes made after commit begins do not trigger a merge.

**Shared status.** Dirtiness lives on the shared effect tree. A batch that defers an effect it collected marks it clean and forces it in every other batch that has it queued, and a real write marks every derived downstream of it however dirty that derived already is, so a reader a deferral left clean is still reached by the next write; staging a fork write leaves the real derived cache status intact; while uncommitted batches exist a write also schedules its effects into its batch when another batch already dirtied them, the batch keeping a membership set of its queue for that time so repeated writes neither grow the queue nor make membership checks scan it. A batch that runs an effect another uncommitted batch has queued forces it in that batch, which runs it again under its own view: the run saw none of that batch's writes, even where the runner's own write to the same source overrode it in the runner's view without counting as hidden (`async-each-overlap`). A run that read a write hidden from it is recorded against the hiding batch: if the hiding batch commits first, the run is forced again in the reading batch; if the reading batch commits first, it is forced in the hiding batch, which runs it under its own view. Forced reevaluation validates the last actual reads rather than executing unconditionally: unchanged values under their declared equality, including derived results and removed dependencies, suppress the rerun. An async expression validates the inputs of the run already belonging to that batch, so a merge need not request completed work again. Deferral retains pending readers without evaluating their derived dependencies; equality is checked when the batch may commit. An unchanged validation still records the writers concealed by its view, so suppressing user code cannot lose the reader's later revisit. Validation of staged structure uses the reads retained by that batch; another batch's last run cannot validate its choice. Async work retains its own run inputs, so unchanged inherited inputs need not start another request. After a view-local read, actual last-read values remain the equality baseline even if the global derived cache returns to its previous value.

**Queued, then resolved.** Scheduling an effect only appends it to the batch receiving the write, and asks for a flush when that batch already started; the batch marks the path from each queued effect to its root when it starts a pass and clears the marks in the same traversal, including under a branch it skips. Marks one batch leaves on the shared effect tree are therefore never seen by scheduling into another, and scheduling never assumes a batch exists — it creates the open one, as the trap of an effect writing what it read and flushing in the same run requires.

**Phases** of one batch's flush:
1. *Structure* — the roots holding queued effects are traversed in creation order; a block whose dependencies changed runs and decides which branches stand. A branch a block skips for this batch is passed over by this batch's traversal, its later passes and its content and effects phases; an entering branch or row is built off-screen with its own effects run. An off-screen branch is hidden from every batch but those that selected it with `unskip`: the others pass over it, and one processing real writes and passing over it along its marks hands the dirty effects there, forced, to the batches that selected it, which run them under their own views, so no batch runs content of a branch its values never selected (invariant 2). A fork clears those marks without waking the selecting batches: speculative writes cannot change their views, and rerunning their async work would replace requests whose inputs did not change. `unskip` also re-queues the dirty effects of a branch the batch had skipped or that some batch passed over. Blocking work under a branch the batch skips or does not show holds nothing: that branch is destroyed or stays off-screen when the batch commits. Every template effect met on the way is collected, dirty or not, and so is every dirty user effect. A held batch stops here.
2. *Commit* — each wave snapshots its registered changes and runs every preparation before any application, then applies them in registration order. Preparation reads the committed structure without invoking transition options; held or fork choices do neither phase until their real commit, and consumers resolve a merged alias separately in each phase. Changes registered by a preparation or application wait for the next wave. Leaving branches begin removal and remain inert until any outros finish, then are destroyed or stashed if a held batch still selects them; entering ones are inserted and rows moved. An outgoing-owned derived uses its last-selected source view with transitive local caches, while direct reads outside that computation retain this batch's view. Speculative selection admits the branch's running reactions to the selecting batch without ending the view still used by its outro callbacks.
3. *Content* — the template effects deferred while the batch was held run first, then the collected ones in collection order, each only if it is still alive and still stale when the phase reaches it, so one that a write earlier in the phase dirtied runs in this batch, as upstream 5.57.3 orders its render effects (`lifecycle-render-order-for-children-5`); one re-dirtied while running is queued again after its run, never re-entered. A block that a write made while a content or user effect ran marks runs right after that effect, ancestors first, so a branch the write deselects is gone before any later effect of it runs (`guard-nested-if-pre`, invariant 2), as upstream's `eager_block_effects` does. An async expression's block is no structure and is not run early: it reruns in the batch the write went to, which requests it once (`async-write-equals-visible-value`).
4. *Effects* — user effects run after content: the deferred ones, then the rest in the order the traversal met them or blocks created them. Only dirty ones are collected: a user effect that an earlier user effect's write dirtied runs in the next batch, after that batch's content, where upstream's collecting every user effect of a dirty branch runs it first (`effect-focus-order`, Svelte #16256). One created during content or effects is queued in the next batch; one created under a boundary showing its pending content waits until the boundary reveals its content. `$effect.pre` effects are content effects: they run at creation and rerun among the template effects in tree order.

Writes made during structure or commit — a teardown's included — join the batch being processed, and the flush repeats structure and commit until nothing is queued, bounded at 1000 passes, before content runs. A value a teardown writes thus deselects its branches before any content of them runs (invariant 2). Upstream 5.57.3 sends writes made after traversal, commit-time teardowns included, to a new batch processed after the current batch's effects have run (`batch.js`, `#process`): the shape of the passed-guard and seat-release traps, where a guard a teardown cleared still let the deselected branch's effects run.

Writes made and work started during content or effects belong to the next batch, which the same flush processes after this one; only the template effects and blocks they reach run earlier, as phases 3 and 4 say. A block's first run — inside a branch being built off-screen, or a mount — inserts at once, since nothing of it is on screen.

**Errors.** An error no handler or boundary takes goes to the failing tree's front end ([[4ece65b4]]). A native tree's is reported to the host and the batch goes on. When the front end rethrows, as Svelte's does, the error propagates out of the flush. First, though, the failing batch hands everything it has not finished — queued and collected effects, the rest of the current phase, registered changes, waiters — to the open batch and clears its path marks. The rest of the tree therefore keeps updating on the next flush, while the effect that threw stays clean until its dependencies change. A failing fork is discarded instead. Exceeding the update depth — 1000 structure passes in one batch, or 1000 batches in one flush — is the exception: the runaway batch is discarded rather than handed on, the effects it queued stay clean until a dependency changes again, and under DEV the stack of each write repeated more than five times in that flush is logged once. `effect_update_depth_exceeded` then goes to the boundary of the last effect queued into the runaway batch, as upstream sends it to its last scheduled effect's boundary, and the flush goes on. With no boundary there it goes to that effect's front end. With nothing queued it is thrown. Handing that work on would restart the loop from the next microtask, forever.

**Nested `flushSync`.** Called during structure or commit, as from a teardown, it returns without processing: the batch in progress is finished by the outer flush. Called during content or effects, it processes the next batch at once, never a batch already being processed. A flush processes uncommitted batches that are ready — work settled, or effects queued into them — in creation order before the open batch. Tasks queued with `task()` — the DOM's deferred steps, such as an await block showing its pending branch — run at the next microtask or when a flush drains them. An automatic flush drains once before processing batches; tasks queued during that processing keep their armed microtask, so an immediately resolved promise can settle before its pending branch appears. An explicit `flushSync` drains before each batch and once more before returning. A microtask armed for a queue a flush already drained runs nothing, so a later task never runs ahead of microtasks queued between.

**Rebase.** When a batch commits, other uncommitted batches rebase onto the committed values. A later batch keeps the sources it wrote itself; those sources cannot invalidate its work when an earlier batch commits. A retained batch, including a fork, adopts a newer same-source write; later own writes and untouched sources remain its own. Fresh assignments, proxy mutations and external emissions carry new write intents across restored or merged identities; an async completion retains the intent of the run it completes. Publication versions identify later dependency events, and assignments are invalidated only when their captured immediate dependency values actually change under equality. Their concealed prewrite base also advances to that commit, so a still-pending write cannot hide a value already shown on screen. Reactions reading a changed source and one of the rebased batch's own writes, together with runs recorded against the commit, are forced under the updated view before that batch may commit. `settled()` called under no owner resolves only once no open or held batch remains, forks aside, and no unit of pending work started outside a fork is outstanding — work under a boundary showing its pending content included, since that content swaps in only when its work settles (invariant 3, `pending-snippet-switch`). Called under an owner, it waits only for that owner's application ([[4ece65b4]]).

**Eager effects.** An eager effect, what `$inspect` runs on, stands outside batches: it runs at its creation and again at the end of the write that reaches it, inside the writer's call stack, reading current values with no view or teardown past, and only when one of its dependencies changed value. A staleness check that throws counts as stale: a derived it evaluates can fail because the tree around it is about to be torn down, and the effect's own error handling — `$inspect` keeps the error until its template effect reports it — must decide, as upstream's `flush_eager_effects` does (`inspect-derived-if-destroy`). A fork's write reaches it only when the fork commits. Under DEV a mutating array method on a `$state` proxy holds eager effects until it returns, so they run once, on the finished array, in the caller's frame. `$state.eager(expr)` (`latest`) is built on one: the reading reaction evaluates the expression outside every view, and an eager effect over the same reads, on its next run, bumps a version source the reader tracks at the next microtask in a flush of its own, so the reader shows the newest value while the batch that wrote it is still held. The version is kept per owner effect, since the tracking frame does not name its reaction.

**Roots.** A mount made without an owner and an `$effect.root` are top-level effects: queued, traversed and committed by the same phases, ordered among themselves by creation (invariant 4). A mount under an application owner is its child; `$effect.root` keeps the caller's context and boundary but is never destroyed with the caller.

**No state of unmounted trees.** The runtime keeps no registry of trees: a batch is dropped once committed or discarded, a unit of pending work settles when the effect that started it is destroyed so an unmounted tree cannot keep a batch held, a root is reachable only from its mount, effects and deriveds unsubscribe from their sources when destroyed — an effect destroyed during its own run included — and `mount` keeps instances in a `WeakMap`. Once an unmounted tree's flush settled nothing in the runtime references it, so a target resets nothing between samples (invariant 5).
